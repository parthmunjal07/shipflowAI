# Database Restore Procedure (Disaster Recovery)

If a critical failure occurs (e.g., accidental dropping of production tables, catastrophic corruption), you can restore the database using the automated logical backups generated by our GitHub Actions workflow.

> [!CAUTION]
> **Data Loss Warning**
> Restoring a database from a backup will overwrite all data that was created *after* the backup was taken. Only perform a full restore in an actual disaster scenario. If possible, restore to a *staging* database first to extract specific missing records instead of rolling back the entire production app.

## Prerequisites

1. **PostgreSQL Client Tools**: You must have `psql` and `gunzip` installed on your machine.
   - macOS: `brew install postgresql`
   - Windows: Install via the PostgreSQL installer or WSL.
   - Linux: `sudo apt install postgresql-client`
2. **Access to Backups**:
   - Go to the **Actions** tab in GitHub.
   - Select the **Database Backup** workflow.
   - Click the latest successful run.
   - Download the artifact attached at the bottom (e.g., `shipflow_backup_2026-06-25_02-00-00.sql.gz`).
3. **Database Credentials**: You need the target `DATABASE_URL` for the database you are restoring *into*.

## Restore Procedure

### Step 1: Download and Extract the Backup
Extract the downloaded `.gz` file:
```bash
# macOS/Linux
gunzip shipflow_backup_2026-06-25_02-00-00.sql.gz

# You should now have an uncompressed file: shipflow_backup_2026-06-25_02-00-00.sql
```

### Step 2: Prepare the Target Database
If you are restoring to an existing database with data, the `pg_dump` file does *not* automatically `DROP` existing tables unless specified. Because Prisma manages our schema, the safest way to restore is to wipe the target schema completely and let the backup recreate it.

1. Connect to the target DB using Prisma Studio or `psql` and verify you are connected to the right instance.
2. Drop the `public` schema and recreate it (this deletes all tables!):
```sql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
GRANT ALL ON SCHEMA public TO postgres;
GRANT ALL ON SCHEMA public TO public;
```

*(Alternatively, use `npx prisma db push --force-reset` to wipe and recreate empty tables, but the `.sql` dump usually contains `CREATE TABLE` statements if taken via the GitHub Action, so an empty schema is preferred).*

### Step 3: Execute the Restore
Run the `psql` command to stream the SQL file into the database. Replace `TARGET_DATABASE_URL` with your connection string.

```bash
psql "TARGET_DATABASE_URL" -f shipflow_backup_2026-06-25_02-00-00.sql
```

### Step 4: Verify the Restore
1. Start your local application pointing to the restored database (`DATABASE_URL=TARGET_DATABASE_URL pnpm dev`).
2. Log in and verify that Organization, Project, and Feature Request data is intact.
3. Check the Prisma migrations table. If Prisma complains about drift, you may need to run `npx prisma migrate resolve --applied <migration_name>` for missing migration records, though logical backups usually include the `_prisma_migrations` table perfectly.

## Verification Schedule
> [!IMPORTANT]
> **Compliance Requirement**
> This restore procedure must be manually tested by the engineering team **once per quarter**. To test, restore the latest production backup into an ephemeral staging database and verify the application successfully boots and serves data.
